# 연구 깊이를 유지하는 개선 작업 명세

이 문서는 검토자가 사용자 저장소를 직접 수정한 결과가 아니라, 로컬 Codex에 전달할 구현·의미 검토 명세다. 작업은 기존 raw와 연구 단계 순서를 보존한다.

## A. Luna에게 전달할 기계적 개선 작업

아래를 하나의 제한된 작업으로 수행하라. 먼저 실제 저장소의 구조를 읽고 기존 파일과 호환되게 구현하라. 새로운 코드 판단이나 문항 풀이, 의미적 귀납을 생성하지 마라.

### 목적과 수정 범위

기존 `scripts/build_question_views.py`와 열람용 파생 산출물을 개선한다. 필요한 독립적인 파싱·검증·색인 모듈을 추가할 수 있다. quota, launcher, handoff, meta 주기, 원래 stage 정의, 원판정, prepared membership은 이번 작업에서 변경하지 않는다.

변경 전 queue/processed/원문 입력의 해시를 기록한다. 연구가 동시에 실행 중이면 일관된 읽기 스냅샷을 사용하고 스냅샷 시점과 원장 끝 record_id를 기록한다. 일관된 스냅샷을 만들 수 없으면 섞인 시점의 결과를 성공으로 발표하지 않는다. 이번 작업 중 이미 있는 semantic raw는 수정·삭제하지 않는다.

### 1. 필드 정규화와 원문 보존

- `primary`, `auxiliary`/`secondary`, `competitors`, `competing_codes`, `competing_codes_refuted` 등 실제 키의 변형을 검사한다.
- 통합된 화면 섹션으로 배치하되 원래 key/value와 source_record_id를 보존한다.
- 해당 키가 없거나 빈 값인 것을 임의로 새 내용으로 채우지 않는다.
- 숫자 주 코드 미확정과 풀이 연산 미기록을 구분한다. unnumbered operation이 기록되어 있으면 그 설명을 그대로 표시한다.
- 낯선 필드를 조용히 버리지 말고 기타 원문 필드로 보존한다.

### 2. 최초 기록과 사후 수정의 분리

- 최신 done을 무조건 ‘최초 blind’로 부르지 않는다.
- 최초 제출, 원문 보충 후 재검토, 정답/태그 공개 후 수정의 record ID와 순서를 구분해 보인다.
- 기존 최초 primary와 후속 current_primary_candidates/revised_primary_candidates가 다르면 두 값을 구분한다.
- `EO #45 → #17/#45 우선순위 유보`, `EJ #80 → #75/#80 우선순위 유보`처럼 raw에 명시된 관계만 기계적으로 표시한다.
- 연결 관계가 명시되지 않으면 Luna가 추론해 최신 최종 판단을 구성하지 않는다.

### 3. 원문·그림·수식·선지 자료 패키징

- 결과 열람본이 사용한 제시문, 보기, 선택지, 선택지 번호 매핑, 이미지, 수식 보충 자료의 실제 파일 경로와 provenance를 수집한다.
- 원문 일부가 빈 문자열, 수식 자리 소실, 선택지 행렬 붕괴, 표시 범위 미확정이면 해당 문항에 경고를 표시한다.
- 기존 verified supplement가 있으면 원래 추출문과 구별하여 포함하거나 상대 링크로 연결한다. 누락 수식이나 그림을 추측해 생성하지 않는다.
- 문항별 선택지 다섯 개가 있어도 모두 비어 있으면 READY가 아니다. CH 같은 사례를 반드시 테스트한다.
- CT처럼 원래 text에서 분수는 사라지고 해설만 복원값을 사용한 경우, 보충 원문이 패키지에 포함되었는지 별도 검사한다.
- 이미지 ‘파일이 존재함’, 원문 일치 ‘기계적 연결됨’, 그림 내용 ‘사람/Astra가 검증함’을 별도 상태로 표시한다.
- 권한 없이 정답/SDSS/해설을 미완료 blind packet으로 복사하지 않는다. 결과 뷰는 완료한 연구의 사후 열람본이며 연구용 blind 입력이 아니다.

### 4. 완료 상태 및 모집단 분리

- prepared manifest 범위의 완료 수와 legacy 완료 수를 별도 표시한다.
- 162/165는 과거 스냅샷 숫자일 뿐 기대값으로 하드코딩하지 않는다.
- 같은 모집단에 대해 case ID 집합 자체를 비교한다. 총수만 같으면 통과시키지 않는다.
- 최소 표시 항목: 풀이 단계 완료, SDSS 태그 확보 여부, 실제 의미 대조 여부, 원문 패키지 완전성, 미해결 주장, 마지막 반영 시점.
- `sdss_compare=done`이지만 태그 미연결인 경우에는 ‘태그 미확보/비교불가’로 표시한다. 이를 태그 일치나 불일치로 세지 않는다.
- `depth_backfill_pending=[]`는 작업 완료 표시다. 원문 backfill에 의미적 유보가 남아 있으면 이를 독립적인 unresolved 항목으로 유지한다.
- source missing, needs review, 노출/보류와 삭제/미등록을 구분한다.

### 5. 코드·경계·실제 수행 색인

- 각 번호별 문항 수와 서로 다른 passage group 수를 따로 집계한다.
- primary와 auxiliary를 혼합 집계할 때는 범위를 명시한다.
- 같은 group/교차 revision record가 여러 파일에 복제되어도 record_id를 기준으로 한 번만 센다.
- meta/audit 원문이 저장소에 실제 있으면 근거에 연결한다. ID만 있는 경우 본문을 새로 만들어 넣지 않는다.
- 필드에 명시된 `counterexample`, `revised_rule`, `unresolved`, `current_primary_candidates` 등을 보존하는 관계 색인을 만든다.
- 코드 출현 빈도를 의미 검증 점수로 바꾸지 않는다.

### 6. 검증

실제 production parser/render 함수에 입력을 주는 fixture로 검사하라.

1. competing_codes가 기타 필드에 있어도 화면의 경쟁 해석 섹션에 빠짐없이 표시됨.
2. 최초 판단과 사후 주 코드 유보가 덮어쓰기 없이 병기됨.
3. CH처럼 선지가 모두 빈 문자열이면 source warning 발생.
4. CT처럼 보충 자산을 참조하지만 export에서 빠지면 broken evidence 경고.
5. SDSS done+빈 태그는 비교일치 통계에서 제외됨.
6. backfill done+carryover 유보는 미해결 항목에 남음.
7. prepared/legacy 범위가 다를 때 각각 집계하고 동일 scope끼리 검증함.
8. 같은 다중 case revision은 중복 합산하지 않음.
9. 같은 입력 스냅샷을 두 번 실행해 case set, 기록 내용, 링크가 같음. 생성 시각만 다른 경우 이를 구분함.
10. 원본 queue/processed/원문 hash가 작업 전후 불변임. 실시간 작성 중인 별도 세션이 있으면 그 변경을 본 작업의 수정으로 혼동하지 말고 보고함.

최종 보고는 변경 파일, 생성 경로, 모집단별 case 수, source/태그/의미 유보 수, 검사 결과, 원본 불변 여부만 출력하라. 연구 재시작은 이 작업에서 자동으로 수행하지 않는다.

## B. Astra High에게 전달할 의미적 연구 작업

기존 deep protocol은 유지한다. 다음은 초반 분석을 얕게 처리하라는 지시가 아니라, 지금 확인된 경계와 설명 단위 문제를 집중 검토하는 추가 연구다.

### 원칙

- 원문의 관계를 먼저 복원하고 코드 이름은 뒤에 붙인다.
- 최초 blind/독립 판정은 덮어쓰지 않는다. 검토 기록은 사후 분석임을 명시한다.
- 새 기출을 풀기 전 해당 문항의 정답/SDSS/기존 해설을 읽지 않는다.
- 원저자 정의가 미확보인 경우 원저자 이론의 오류나 글로벌 코드 통합을 확정하지 않는다.
- 아래 후보 수행군은 가설이며 결론이 아니다. 맞지 않는 사례도 기록한다.

### 작업 1. 코드 판정 단위 검토

DV/GA를 비교한다. 두 경우 모두 P→Q를 P∧¬Q의 반례로 기각하는지 원문과 선지를 확인하라. 필요조건이라는 관계 형식과 반례 사용이라는 증거 방식을 분리하고, 어느 코드가 ‘정답 선지’, ‘결정 연산’, ‘증거 유형’을 대표하는지 표시하라. 기존 번호는 보존한다.

각 분석에 다음을 남겨라.

- 발문의 과제 및 긍정/부정 선택 방향
- 판정 대상: 문항 전체/선지/선지의 절/지문 관계
- 근거 원문 및 위치
- 원문 관계와 선지에서 바뀐 부분
- 직접 함의/합성 함의/명시적 반례/지지 부족/미해결 중 근거 유형
- 기존 code와 역할·범위, 후보 우선순위가 유일한지 여부

### 작업 2. 가장 강한 대안 풀이를 통한 경쟁 경계

EO/DZ/EP와 EJ를 anchor로 사용한다. 경쟁 코드를 정보가 빠진 약한 표로 표현해 기각하지 말고, 태도나 입력 관계를 포함하는 가장 강한 대안 표현을 실제로 구성하라.

판정은 다음 중 하나로 남겨라.

- 경쟁 설명이 실제 오류를 놓치므로 배제
- 같은 국소 수행의 다른 표현
- 상위 과제/하위 관계의 층 차이
- 별개의 추가 수행이 필요
- 현재 표본으로 미결

검토할 수 있는 실제 경쟁이 없으면 빈 수를 채우기 위해 무관한 번호를 추가하지 않는다. 검토 깊이를 줄이지 않고 근거 있는 경쟁에 집중한다.

### 작업 3. 보존 범위의 교차 지문 검증

AB/BZ/CT/GC를 직접 비교하라. 바뀐 요소, 유지된 요소, 유지의 원문 근거, 잘못 확장된 예외 범위가 무엇인지 표시한다.

‘예외이면 나머지는 항상 유지된다’로 과잉 일반화하지 않는다. 일반 규칙과 특례의 적용 범위가 원문에서 확인될 때만 이 구조를 사용한다. 복원 수식·이미지가 필요하면 확보된 자료를 명시하고 없는 자료는 의미로 추측하지 않는다.

### 작업 4. 문맥 의미의 양방향 반례

FH/FN/FT/GJ/ET에서 대상 명사 동일성, 물리/비물리 구별, 행위·상태·평가·결과 성분을 분리한다. 학생이 실제로 사용할 수 있는 판독 절차를 제안하되 하나의 쉬운 분류로 모든 사례를 해결한다고 주장하지 않는다.

### 작업 5. 이유·관점·비교 산출의 분리

FF/FL에서 이유를 인과적 생성과 개념적 구성으로 나눌 근거를 확인한다. FX/EF에서 사실 진위와 관점·목적에 대한 적합성을 분리한다. FD/EI에서 공통 질문과 공통 동의를 구별한다.

### 작업 6. 검토용 최소 변형과 다음 표본

각 중요한 후보 규칙에 대해 한 부분만 바꾼 검토용 변형을 작성한다. 예: FV의 수용 대상, EP의 과정 조건, EJ의 태도 표지, FX의 평가 관점.

- 변형이 어느 결론을 바꿔야 하는지 사전에 명시한다.
- 변형 문제는 실제 기출 표본 수에 합산하지 않는다.
- 다음 미열람 지문에서 규칙의 성립뿐 아니라 실패 조건을 찾는다.
- 같은 지문의 여러 문항이나 같은 revision 복제본을 독립된 반복 근거로 세지 않는다.
- 새로운 코드 번호를 확정하기보다 기존 번호와 수행군 후보의 대응을 보존한다.

최종 산출물은 사례별 판단, 교차 지문 경계, 유지/수정/유보, 반례 후보, 학생 행동, 생성 원리, 다음 기각 조건을 포함하라. 분량 점수나 자기평가 9/10만으로 품질을 결론내리지 않는다.
