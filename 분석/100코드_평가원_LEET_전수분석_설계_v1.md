# 100코드 평가원·LEET 전수 분석 설계 v1

## 0. T01~T22의 출처 정리

`T01~T22`는 외부 저작자의 기존 코드표를 옮긴 것이 아니다. 이 프로젝트에서 평가원식 선지를 만들기 위해 다음 자료를 종합해 임시로 만든 **오답 변형 분류**였다.

1. 사용자가 제공한 기술 지문 제작 피드백
   - 논리 코드의 표백화
   - 부분과 전체, 양과 질의 혼동
   - 주체·객체·범주의 교란
   - 비례 연쇄의 중간 매개 생략
   - 경계 조건과 극한 상황
   - 단계 간 교차 오염
   - 앞부분의 참 진술 뒤에 잘못된 귀결을 붙이는 방식
2. 로컬 평가원 사회·경제 지문의 선지 분석
   - 시점 이동, 적용 범위 이동, 비교축 변경, 가능·필연 교환 등
3. 생성 문항을 검수하면서 반복된 오류를 제작 규칙으로 일반화한 결과

따라서 T체계에는 경험적 근거가 있지만, 다음과 같은 한계가 있다.

- 이원준의 100코드처럼 독립적인 이론 체계나 공개된 기출 색인이 아니다.
- 지문과 문항의 논리 구조보다 **오답을 어떻게 변형하는가**에 초점이 있다.
- T01~T22의 원표가 현재 작업공간에 저장되어 있지 않아, 항목명과 번호를 정확히 복원하려면 원래 표가 다시 필요하다.

앞으로 T체계를 유지한다면 이름을 `T코드`보다 `D-변형` 또는 `오답 변형 연산자`로 바꾸는 편이 정확하다.

## 1. T체계와 100코드의 관계

두 체계는 경쟁 관계가 아니라 분석 층위가 다르다.

| 구분 | 이원준 100코드 | 프로젝트 T01~T22 |
|---|---|---|
| 주된 질문 | 지문·문항에 어떤 관계가 있는가? | 정선지의 무엇을 바꾸어 오답을 만들었는가? |
| 분석 대상 | 개념, 집합, 인과, 논증, 수리 관계 | 주체, 대상, 시점, 방향, 범위, 수치 등의 변형 |
| 사용 시점 | 지문 설계와 문항 풀이 | 선지 제작과 오답 검수 |
| 기출 색인 | sdss.kr 검색 DB가 있음 | 독립된 외부 색인 없음 |
| 관계 | 하나의 코드에 여러 변형이 대응 가능 | 하나의 변형이 여러 코드를 위반할 수 있음 |

## 2. 전수 분석에 DB가 필요한 이유

sdss.kr 검색 결과만으로는 `왜 이 코드인가`를 검증할 수 없다. 최소한 다음 자료가 함께 있어야 한다.

- 지문 전체
- 발문
- ①~⑤ 전체 선지
- 정답
- 표·그래프·그림 원본
- 시험명, 연도, 영역, 문항 번호
- 가능하면 공식 정답표와 정답률

코드의 근거는 대개 지문의 한 문장이 아니라 `지문 근거 A + 지문 근거 B + 선지의 변형 지점`에서 드러난다. 제목과 코드명만으로는 이 연결을 설명할 수 없다.

### 3.3 sdss.kr 코드 색인

사이트는 다음 용도로 사용한다.

- 코드별 후보 문항 검색
- 한 지문의 문항별 코드 차이 확인
- 평가원·LEET·MEET의 비교 사례 탐색
- 분석 우선순위 선정

다음 용도로는 사용하지 않는다.

- 사이트 태그를 검증 없이 정답 라벨로 확정
- 추정 정답률을 공식 통계로 사용
- 코드가 비어 있는 문항을 무코드 문항으로 판정
- 지문 원문을 보지 않고 코드의 이유를 서술

## 5. `왜 이 코드인가`의 판정 규칙

문장에 코드의 별칭이 보인다는 이유만으로 태그하지 않는다. 다음 순서를 따른다.

1. **정답 결정 정보 확인**: 이 관계가 없으면 정답을 고를 수 없는가?
2. **최소 충분 코드 선정**: 정답을 가장 적은 수의 코드로 설명한다.
3. **주 코드와 보조 코드 분리**: 정답을 직접 결정하는 코드와 풀이를 보조하는 코드를 나눈다.
4. **대안 코드 기각**: 비슷해 보이는 코드가 왜 주 코드가 아닌지 적는다.
5. **오답 역검증**: 각 오답이 어느 관계를 어떻게 위반했는지 확인한다.
6. **근거 위치 표시**: 지문 문장, <보기> 조건, 선지 변형을 연결한다.

### 예시

`가격이 오르면 수요량이 감소한다`는 문장에는 #12 조건문과 #46 인과관계가 함께 보일 수 있다. 그러나 문항이 다른 조건을 고정한 채 가격 변화만 적용하게 한다면 주 코드는 #43 타변수통제가 될 수 있다. 반대로 가격→수요량→매출액의 중간 경로를 복원해야 한다면 #45 함수 또는 #46 인과관계가 주 코드가 된다.

## 6. 100코드 전수 분석 단위

각 코드마다 다음 형식의 코드 카드를 만든다.

```text
#번호 코드명

1. 원본 별칭과 기본 정의
2. 인접 코드와의 경계
3. 평가원 대표 문항
4. LEET 대표 문항
5. 지문 근거
6. 정답 판단 과정
7. 왜 이 코드인가
8. 함께 쓰인 보조 코드
9. 대표 오답 변형
10. 생성용 문장 표백 예시
11. 통합사회 토픽 적용 가능성
12. 검증 상태와 출처
```

### 표본 수 원칙

- 코드별로 평가원 2개, LEET 2개 이상을 우선 목표로 한다.
- 사례가 부족한 코드는 MEET 등 사이트 수록 시험을 보조 표본으로 쓴다.
- 실제 사례를 찾지 못하면 억지로 채우지 않고 `검증 표본 부족`으로 표시한다.
- 복합 코드 문항은 주 코드와 보조 코드를 각각 판정한다.

## 7. 작업 순서

### 1단계: T01~T22 원표 복구와 비교

- 원래 T표의 항목명·정의·예시 확보
- 100코드와 다대다 대응표 작성
- 중복 T항목 통합
- 코드가 아니라 변형 연산자인 항목은 명칭 변경

상태: **부분 완료**. T01~T22는 외부 코드가 아니라 프로젝트 내부 오답 변형 분류였음을 확인했다. 원표 파일이 없어 번호별 원형 복구는 불가능하므로, 앞으로는 독립 코드가 아닌 `오답 변형 연산자`로만 취급한다.

### 2단계: 평가원 DB 보완

- 163세트를 지문·문항 단위 JSONL로 정규화
- 공식 정답표 결합
- 누락된 표·그래프 추출
- 중복 세트·문항 번호 검증

상태: **정답·텍스트 정규화 완료**. 시각 선지 불완전 22문항은 별도 대조 대상이다.

### 3단계: LEET DB 구축

- 공식 연도별 PDF·정답표 수집
- 지문·문항·선지·이미지 추출
- 연도·문항 메타데이터 정규화
- 원문과 추출본의 페이지별 대조

상태: **홀수형 코퍼스 구축 및 검증 게이트 완료**. 코드 확정 시 문항 단위 재대조를 유지한다.

### 4단계: 사이트 코드 라벨 결합

- CodeName별 검색 결과 수집
- 시험·연도·문항 번호로 원문 DB와 조인
- 빈 코드, 복합 코드, 표기 변형 정리

상태: **완료**. 100개 코드, 코드 적중 1,492행, 고유 후보 문항 1,147개를 수집했고 그중 공식 정답 비교가 가능한 756건은 전부 일치했다. 로컬 연결 큐는 `data/code_candidate_review_queue_by_code.jsonl`이다.

## 9. 현재 판단

- 평가원 DB: **정규화·공식 정답 연결 완료** — 163지문, 678문항, 정답 연결 678/678
- LEET DB: **홀수형 정본·정답·시각 자료 검증 완료** — 개별 코드 확정 시 문항 단위 재대조
- 코드 색인: **수집·로컬 연결 완료** — 사이트 표지는 제3자 후보로만 사용
- T01~T22: **출처 성격 정리 완료** — 외부 코드가 아니라 내부 오답 변형 연산자이며 원표 파일은 없음
- 100코드 본판독: **#1~#100 1차 판독 완료**

따라서 다음 작업은 `MEET 정본 검증 → 1,147개 후보의 주·보조 코드 확정 → 오답별 변형 연산자 기록 → 통합사회 분야별 생성 레시피 반영`이다. 1차 판독 완료는 코드의 의미와 경계를 정리했다는 뜻이며, 사이트 후보 1,147개 전부의 문항별 최종 태깅이 끝났다는 뜻은 아니다.
